# [Spec] M1 前端实施与后端对接（mock 全功能 → 对接）

> status: ready-for-agent
> supersedes: 0001-m1-core-board.md 的前端部分（0001 仍为后端与总纲的权威）

## Problem Statement

Kanso 后端 M1 已交付并全绿（45 个 HTTP 合约测试，27 条路由，WebSocket 实时，级联删除，事件契约）。前端处于 mock 阶段（MSW + 从真实后端导出的种子数据），但存在明确的功能缺口与契约风险：

- **删除确认缺失**：spec 0001 明文要求删工作区/项目/列/任务时 UI 需确认，当前前端一个确认都没有。
- **标签库管理缺失**：spec 要求工作区级创建（名称+颜色）/重命名/删除标签，当前只有任务卡片上的贴/摘。
- **排序功能悬空**：`sort-tasks` 有完整实现与 9 个测试，但未接入任何页面；且其字段（priority/dueDate/number）后端 task 表不存在。
- **添加任务有延迟感**：createTask 无乐观更新，任务要等 refetch（mock 100-400ms 延迟）才出现，用户感知为"第一次才成功"。
- **类型漂移**：`Project.updatedAt` 已加入类型但 mock 数据/测试未同步，tsc 门槛曾挂 6 处。
- **dashboard/settings 依赖后端不存在的端点**（`/api/dashboard`、`/api/settings/backup`），对接时后端必须补齐。
- **mock 无 WebSocket**：spec 的"双窗口实时同步"在 mock 下无法验证，需明确放到对接后验证。

目标：前端在 mock 下功能全量可用且测试全绿，随后对接真实后端（补 2 个端点），最终双窗口实时验证通过。

## Solution

前端补齐 spec 0001 的 8 大类 User Stories 的全部缺口，加上 dashboard/settings 两个页面；后端新增 2 个端点（dashboard 聚合、备份导出）。验收标准 = mock 全功能 + vitest/tsc/Playwright 全绿，然后 `VITE_USE_MOCK=false` 对接后端，双窗口实时验证放对接后。

## User Stories

### 访问与身份

1. 作为用户，我首次打开 Kanso 时看到登录页并输入 Access Key，以便进入系统。
2. 作为用户，当我输入错误的 Access Key 时看到明确错误提示，以便知道密钥不对。
3. 作为用户，登录成功后刷新页面无需重新输入密钥，以便保持使用状态。
4. 作为用户，当服务端密钥变更导致我的密钥失效时，我被清除本地密钥并引导回登录页，以便重新输入新密钥。
5. 作为用户，我无法注册账号或切换身份——只有一个固定 Admin Identity，以便系统保持简单。

### Workspace（工作区）

1. 作为用户，首次启动后我能看到自动种子的默认工作区，以便直接开始使用。
2. 作为用户，我能查看当前工作区及其下项目列表，以便了解我有哪些项目。
3. 作为用户，我能创建新工作区、重命名工作区，以便组织不同业务域。
4. 作为用户，删除工作区时其下所有项目一并删除，且弹出自定义确认框，以便清理废弃空间而不误删。

### Project（项目）

1. 作为用户，我能在工作区中创建项目（输入名称），以便为不同工作建立独立看板。
2. 作为用户，创建项目时系统自动生成默认列（待办/进行中/已阻塞/已完成），以便开箱即可用。
3. 作为用户，我能重命名项目，以便名称反映项目最新含义。
4. 作为用户，我能删除项目（其下列与任务级联删除），且弹出自定义确认框，以便清理废弃项目。
5. 作为用户，我能从项目列表进入任意项目的看板，以便查看其任务。
6. 作为用户，我能通过直达链接（含项目与任务 ID）直接打开看板或任务详情，以便分享链接给同事。

### Board / Column（看板与列）

1. 作为用户，我能在看板上看到项目下的列，每列顶部显示列名与任务数，以便快速了解分布。
2. 作为用户，我能创建列（输入名称），以便定义我的工作阶段。
3. 作为用户，我能重命名列，以便阶段名随时调整。
4. 作为用户，我能横向拖拽列来调整列的顺序，以便按真实流程排列阶段。
5. 作为用户，删除列时其内任务一并删除，且弹出自定义确认框，以便清理无用阶段。
6. 作为用户，空列显示空状态提示，以便知道该阶段没有任务而非异常。
7. 作为用户，我能在看板顶部切换排序字段与方向（标题/创建时间），以便按需查看任务顺序；排序只改变显示顺序，不改变拖拽定的 position，以便排序与拖拽语义互不干扰。

### Task（任务）

1. 作为用户，我能在任意列的底部"添加任务"创建任务（先输入标题），以便快速记录工作项。
2. 作为用户，添加任务后任务立即出现在列中（乐观更新），无需等待重新拉取，以便操作有即时反馈。
3. 作为用户，我能编辑任务标题与描述（富文本纯文本即可），以便补充任务细节。
4. 作为用户，我能把任务拖拽到其他列，以使其进入新阶段。
5. 作为用户，我能在同一列内拖拽任务调整顺序，以便按优先级排列。
6. 作为用户，拖拽任务时界面立即响应（乐观更新），移动失败时回滚并提示，以便操作流畅且不丢数据。
7. 作为用户，我能删除任务，且弹出自定义确认框，以便移除不再需要的工作项。
8. 作为用户，任务卡片显示标题、标签、负责身份（固定 Admin Identity 显示为"我"），以便一眼看清关键信息。
9. 作为用户，我能点击任务卡片打开任务详情页，以便查看/编辑完整信息。
10. 作为用户，我能看到任务所属项目与列，以便知道它在哪里。

### Label（标签）

1. 作为用户，我能在工作区页管理标签库：创建标签（名称 + 预置色板选色）、重命名、删除，以便建立共享的分类体系。
2. 作为用户，我能给任务贴标签、移除标签，以便对任务分类。
3. 作为用户，同一任务可贴多个标签，以便多维分类。
4. 作为用户，标签在看板卡片与详情页以彩色徽章显示，以便快速识别。
5. 作为用户，删除标签后任务上该标签消失，以便维护标签库。

### Comment（评论）

1. 作为用户，我能在任务详情中发表评论，以便讨论任务进展。
2. 作为用户，我能看到每条评论的作者（Admin Identity）与时间，以便知道讨论脉络。
3. 作为用户，我能删除评论，以便修正误发内容。

### Activity（活动记录）

1. 作为用户，我能在任务详情看到该任务的完整活动流（创建、改名、移动列、贴标签、评论等），按时间倒序，以便追溯任务演变。
2. 作为用户，活动记录标注操作类型与时间（作者固定为 Admin Identity），以便快速定位变化。

### Realtime（实时同步，对接后验证）

1. 作为用户，两个浏览器同时打开 Kanso 时，我在一个页面新建/移动任务，另一个页面无需刷新即看到更新，以便多人协同。
2. 作为用户，我的 WebSocket 断开（如网络抖动）后自动重连，重连后重新拉取最新数据，以便状态最终一致。
3. 作为用户，我只收到与当前所在项目相关的实时事件，以便避免无关流量。

### Dashboard（仪表盘）

1. 作为用户，我能在 dashboard 看到总任务数、本周新增、紧急数、完成进度环形，以便快速了解整体进展（2026-08 改造：移除待办/进行中状态卡——原按列名硬编码，列重命名即失效；完成口径改为末列，见 spec 0001）。
2. 作为用户，我能在 dashboard 看到按列分布、各项目完成度、近 14 天新增/完成趋势折线图，以便定位瓶颈。
3. 作为用户，我能在 dashboard 看到需要关注的任务（紧急）与最近活动，以便优先处理。

### Settings（设置）

1. 作为用户，我能在设置页看到当前登录密钥（可遮蔽/显示），以便确认自己使用的密钥。
2. 作为用户，我能一键导出数据备份（JSON 快照下载），以便内网自用时留存数据。
3. 作为用户，设置页显示关于信息（版本等），以便了解部署环境。

### 体验与健壮性

1. 作为用户，页面加载数据时看到加载态而非白屏，以便知道系统在工作。
2. 作为用户，API 错误时看到可读的错误提示（网络/鉴权/服务端分类），以便知道如何应对。
3. 作为用户，操作失败后我的输入不被静默丢弃，以便我能重试。
4. 作为用户，浏览器前进/后退与刷新保持当前页面位置（react-router），以便导航符合直觉。
5. 作为用户，所有破坏性删除（工作区/项目/列/任务）都经自定义确认框，确认后执行、取消后不动数据，以便操作可控。

## Implementation Decisions

- **范围**：spec 0001 的 8 大类 User Stories 全部 + dashboard/settings 两个 spec 外页面（用户已确认全量实施）。
- **删除确认**：自建轻量 Modal 组件（确认/取消），工作区/项目/列/任务四个删除操作统一复用；不用浏览器原生 confirm，不引入 shadcn/Radix 依赖。
- **标签库管理**：位于工作区页（项目列表页）。创建 = 名称 + 预置固定色板选色（spec 0001 既定：色板前端渲染，label 表存颜色标识）；支持改名、删除；删除后任务徽章消失（mock handler 已级联）。
- **排序**：看板顶部排序切换器（字段 + 方向）。**显示层排序**：只改变渲染顺序，不写回 position，刷新/拖拽后恢复。排序字段**仅保留后端存在的**：标题、创建时间（position 本身即排序依据，不作为切换字段）。priority/dueDate/number 是前端预留字段，后端 task 表不存在，排序 UI 不提供入口。
- **乐观更新（createTask）**：用服务端返回的任务立即写入本地看板缓存（`addTaskToBoard` 纯函数），`invalidateBoard` 后台收敛；失败不产生乐观值（无 onMutate 快照，POST 失败即报错）。与已有 moveTask/moveColumn 乐观模式互补。
- **后端新增端点（对接时，spec 外扩展）**：
  - `GET /api/dashboard`：按前端 mock 的 `DashboardData` 契约返回（totalTasks/urgent/newThisWeek/doneTasks/completionPercent/byColumn/projects/focus/recentActivity/trend；2026-08 仪表盘改造：移除 todo/inProgress/byLabel，新增 trend 14 天新增/完成序列，完成口径=末列见 spec 0001），数据源为现有各表的聚合查询。
  - `GET /api/settings/backup`：返回全量数据 JSON 快照（workspaces/projects/boards/taskDetails/labels），**只导出不恢复**（恢复=覆盖数据库，不做）。
- **对接方式**：前端验收通过后 `VITE_USE_MOCK=false`（`.env.development`），`useRealtime` 自动恢复 WS 订阅；后端补 2 端点；冒烟测试重跑；双窗口实时验证作为最终验收项。
- **mock 契约即对接契约**：mock handlers 是前端对 REST 契约的完整实现，对接时后端按 mock 响应形状实现，前端除关闭 mock 外无需改动（ADR-0004：两侧自有类型，字符串即合约）。
- **已修复项（本 spec 落地前）**：createTask 乐观插入；`Project.updatedAt` 类型漂移（seed-data 注入 updatedAt、测试文件补字段、handlers 创建项目补 updatedAt）。

## Testing Decisions

- **好测试的定义**：只测外部行为（HTTP 状态码/响应体、UI 上的可见结果、时序行为），不测实现细节。
- **沿用现有三层测试缝，不新增**：
  1. **后端 HTTP 合约缝**（`internal/httpapi/router_test.go`，httptest + 临时目录真实 SQLite）：新增 `/api/dashboard`、`/api/settings/backup` 的契约测试（状态码、形状、数据一致性）。
  2. **前端 vitest 纯函数**（`web/src/hooks/__tests__/`、`web/src/lib/__tests__/`）：`addTaskToBoard` 已有 5 个测试；排序相关逻辑（限字段后）补充测试。
  3. **前端 Playwright E2E 交互缝**（`web/e2e/`，现有 smoke/visual-compare 同一缝）：新增 4 类交互测试——
     - 乐观更新：拦截看板 GET 并挂起，断言任务在响应返回前出现（抓"添加任务延迟"类回归）；
     - 删除确认：四处删除均弹确认、确认后删除、取消不删；
     - 标签库管理：创建（名称+色板选色）/改名/删除/贴摘全链路；
     - 排序切换：切换字段/方向生效、position 不变。
- **门槛**：`tsc --noEmit` 全绿（spec 0001 既定前端门槛）。
- **WS 实时验证放对接后**：mock 模式无 WebSocket，双窗口同步/断线重连/项目隔离以对接后手工双窗口验证为准（后端已由 0001 测试缝锁定 WS 行为）。

## Out of Scope

- 任务优先级、截止日期、编号（priority/dueDate/number）：后端不加字段，前端排序 UI 不提供入口（0001 Out of Scope 明确不做）。
- 备份恢复（导入覆盖数据库）：只导出。
- 通知、搜索（FTS5）、自动化（Workflow Rule）、工时、MCP/AI 集成、公开分享（沿用 0001）。
- 多用户/成员/角色/权限（Full-access Mode）。
- 子任务、循环/重复任务（沿用 0001）。
- i18n、深色主题（沿用 0001）。
- 前端 E2E 基建之外的测试层（性能测试、视觉回归自动化等）。

## Further Notes

- 本 spec 是 0001 的前端落地补充：0001 定义后端与总纲，本 spec 定义前端实施范围、交互决策与对接契约。
- 前端 mock 阶段的 seed-data 由真实后端导出（勿手改数据，改数据走重导或 handlers 内存态）。
- 拖拽乐观更新与 WS invalidate 可能短暂不一致（乐观值 vs 服务端 reindex 值），以服务端广播为准收敛，前端不做冲突解决（沿用 0001）。
- 对接时的已知偏差记录：任务顺序批量提交端点未实现（前端用单 PATCH，行为等价）；activity 由任务详情聚合返回；WS 密钥走查询参数（浏览器限制）；WS Origin 放行所有 http(s)（内网可接受）。
