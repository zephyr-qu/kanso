# [Spec] M1 核心看板 MVP

## Problem Statement

Kanso 目前只有 M0 骨架：后端能启动、健康检查与访问密钥校验可用、前端是一个"骨架已就位"的占位页。用户打开 Kanso 想管理内网项目任务时，什么都做不了——没有项目、没有看板、没有任务，也看不到任何数据。M1 的目标是把 Kanso 从"能启动"变成"能用"：完整交付 ADR-0003 定义的 Slim Scope 核心看板。

## Solution

M1 交付完整可用的核心看板 MVP：

- 首次进入输入 **Access Key** 登录，通过后看到 **Workspace**（首启自动种子默认工作区）
- 工作区下管理 **Project** 列表；进入项目看到 **Board**（多列 **Column** + **Task**）
- 任务可在列间拖拽移动、同列拖拽排序；支持 **Label** 标记、**Comment** 讨论、**Activity** 操作轨迹
- 所有操作经 **WebSocket** 实时广播到其他打开的页面，多端看到同一状态
- 所有请求以固定 **Admin Identity** 执行，**Full-access Mode**，无账号体系

## User Stories

### 访问与身份

1. 作为用户，我首次打开 Kanso 时看到登录页并输入 Access Key，以便进入系统。
2. 作为用户，当我输入错误的 Access Key 时看到明确错误提示，以便知道密钥不对。
3. 作为用户，登录成功后刷新页面无需重新输入密钥，以便保持使用状态。
4. 作为用户，当服务端密钥变更（如容器重建后重新随机生成）导致我的密钥失效时，我被清除本地密钥并引导回登录页，以便重新输入新密钥。
5. 作为用户，我无法注册账号或切换身份——只有一个固定 Admin Identity，以便系统保持简单（Full-access Mode）。

### Workspace（工作区）

1. 作为用户，首次启动后我能看到自动种子的默认工作区，以便直接开始使用。
2. 作为用户，我能查看当前工作区及其下项目列表，以便了解我有哪些项目。
3. 作为用户，我能创建新工作区、重命名工作区，以便组织不同业务域。
4. 作为用户，删除工作区时其下所有项目一并删除，以便清理废弃空间（UI 需确认）。

### Project（项目）

1. 作为用户，我能在工作区中创建项目（输入名称），以便为不同工作建立独立看板。
2. 作为用户，创建项目时系统自动生成默认列（待办/进行中/已完成），以便开箱即可用。
3. 作为用户，我能重命名项目，以便名称反映项目最新含义。
4. 作为用户，我能删除项目（其下列与任务级联删除，UI 需确认），以便清理废弃项目。
5. 作为用户，我能从项目列表进入任意项目的看板，以便查看其任务。
6. 作为用户，我能通过直达链接（含项目与任务 ID）直接打开看板或任务详情，以便分享链接给同事。

### Board / Column（看板与列）

1. 作为用户，我能在看板上看到项目下的列，每列顶部显示列名与任务数，以便快速了解分布。
2. 作为用户，我能创建列（输入名称），以便定义我的工作阶段。
3. 作为用户，我能重命名列，以便阶段名随时调整。
4. 作为用户，我能横向拖拽列来调整列的顺序，以便按真实流程排列阶段。
5. 作为用户，删除列时其内任务一并删除（UI 需确认），以便清理无用阶段。
6. 作为用户，空列显示空状态提示，以便知道该阶段没有任务而非异常。

### Task（任务）

1. 作为用户，我能在任意列的底部"添加任务"创建任务（先输入标题），以便快速记录工作项。
2. 作为用户，我能编辑任务标题与描述（富文本纯文本即可），以便补充任务细节。
3. 作为用户，我能把任务拖拽到其他列，以使其进入新阶段。
4. 作为用户，我能在同一列内拖拽任务调整顺序，以便按优先级排列。
5. 作为用户，我能删除任务（UI 需确认），以便移除不再需要的工作项。
6. 作为用户，任务卡片显示标题、标签、负责身份（固定 Admin Identity 显示为"我"），以便一眼看清关键信息。
7. 作为用户，我能点击任务卡片打开任务详情页，以便查看/编辑完整信息。
8. 作为用户，我能看到任务所属项目与列，以便知道它在哪里。

### Label（标签）

1. 作为用户，我能在工作区级别创建标签（名称 + 颜色），以便建立共享的分类体系。
2. 作为用户，我能给任务贴标签、移除标签，以便对任务分类。
3. 作为用户，同一任务可贴多个标签，以便多维分类。
4. 作为用户，标签在看板卡片与详情页以彩色徽章显示，以便快速识别。
5. 作为用户，我能重命名/删除标签，删除后任务上该标签消失，以便维护标签库。

### Comment（评论）

1. 作为用户，我能在任务详情中发表评论，以便讨论任务进展。
2. 作为用户，我能看到每条评论的作者（Admin Identity）与时间，以便知道讨论脉络。
3. 作为用户，我能删除评论，以便修正误发内容。

### Activity（活动记录）

1. 作为用户，我能在任务详情看到该任务的完整活动流（创建、改名、移动列、贴标签、评论等），按时间倒序，以便追溯任务演变。
2. 作为用户，活动记录标注操作类型与时间（作者固定为 Admin Identity），以便快速定位变化。
3. 作为用户，当活动因任务/项目删除而失去归属时，活动随上级级联删除，以便不残留孤儿数据。

### Realtime（实时同步）

1. 作为用户，两个浏览器同时打开 Kanso 时，我在一个页面新建/移动任务，另一个页面无需刷新即看到更新，以便多人协同。
2. 作为用户，我拖拽任务时界面立即响应（乐观更新），移动失败时回滚并提示，以便操作流畅且不丢数据。
3. 作为用户，我的 WebSocket 断开（如网络抖动）后自动重连，重连后重新拉取最新数据，以便状态最终一致。
4. 作为用户，我只收到与当前所在项目相关的实时事件，以便避免无关流量。

### 体验与健壮性

1. 作为用户，页面加载数据时看到加载态而非白屏，以便知道系统在工作。
2. 作为用户，API 错误时看到可读的错误提示（网络/鉴权/服务端分类），以便知道如何应对。
3. 作为用户，操作失败后我的输入不被静默丢弃，以便我能重试。
4. 作为用户，浏览器前进/后退与刷新保持当前页面位置（react-router），以便导航符合直觉。

## Implementation Decisions

- **数据访问采用 sqlc**（按 ADR-0004 既定选型）：M0 的手写 SQL 在 M1 换成 sqlc 生成代码，迁移仍为手写 SQL 文件 + 启动自动执行。若落地中 sqlc 成本明显高于收益，可回退为手写 SQL + repository 接口，但需记录该偏差。
- **实体与表**（约 8 张核心表，不含 schema_migrations）：workspace / project / column / task / label / task_label / comment / activity。任务无独立 assignee 表——负责人固定为 Admin Identity（不入库，符合 ADR-0002）。所有实体 ID 沿用现有 32 字符随机 hex；时间统一 UTC ISO-8601。
- **排序语义**：column 与 task 各持有整数 position。拖拽 = 一次 PATCH 提交目标位置，服务端按整个列表重排序（reindex）后广播。不做分数排序（避免浮点漂移的复杂度）。
- **级联删除**：workspace→project→column→task→(comment/label 关联/activity) 逐级级联；activity 随其归属实体删除，不保留孤儿记录。
- **创建项目自动种子默认列**：待办 / 进行中 / 已完成（与 kaneo 参考一致），位置 0/1/2。
- **评论即活动**：发表评论同时写入一条 activity（verb=comment），保证活动流覆盖全部交互；其余写操作（创建/改名/移动/贴标签/删除）在 service 层统一记录 activity。
- **REST API 合约**（全部在 /api 下，除健康检查与 /auth/verify 外经 Access Key 中间件）：
  - 认证：`POST /api/auth/verify`（M0 已有，保持）
  - workspace：`GET/POST /api/workspaces`、`PATCH/DELETE /api/workspaces/:id`
  - project：`GET /api/workspaces/:id/projects`、`POST`、`PATCH/DELETE /api/projects/:id`
  - board：`GET /api/projects/:id` 返回列 + 任务 + 标签的一次性聚合（看板页单次拉取）；列与任务的 CRUD 以嵌套路由表达，`PATCH /api/columns/:id`（含 position）支持列重排，`PATCH /api/tasks/:id`（含 column_id + position）支持移动/重排，另设任务顺序批量提交端点供整列重排
  - label：工作区级 CRUD（schema 既定：label 挂在 workspace 下）+ `POST/DELETE /api/tasks/:id/labels/:labelId` 贴/摘
  - comment：`GET/POST /api/tasks/:id/comments`、`DELETE /api/comments/:id`
  - activity：`GET /api/tasks/:id/activity`（任务详情页活动流）
  - 实时：`GET /api/ws?project=:id` 升级 WebSocket，握手时校验 Bearer Key；事件负载 `{ type: 实体+动词, entity, payload }`，按项目订阅广播（单实例内存 hub，无 Redis，符合 ADR-0005）
- **前端结构与路由**（按 ADR-0004）：`/login`（密钥输入，调用 /auth/verify）、`/w/:id`（工作区项目列表）、`/w/:id/p/:pid`（看板）、`/w/:id/p/:pid/t/:tid`（任务详情）。Zustand 管当前工作区/项目与侧边栏等 UI 态；TanStack Query 管服务端数据——拖拽走 mutation 乐观更新，收到 WS 事件后 invalidate 相关 query key 兜底；现有 `api.ts` 的 Bearer/401 清 key 逻辑原样沿用。
- **标签颜色**：预置固定色板（前端渲染），label 表只存颜色标识符。
- **删除确认**：所有破坏性删除（workspace/project/column/task）在前端弹确认，后端照常执行并返回 204。

## Testing Decisions

- **唯一测试缝：HTTP API 合约层**。测试用 `httptest.NewServer` 挂载真实 chi 路由，连临时目录中的真实 SQLite（执行真实迁移 + 种子），以 HTTP 客户端驱动全部断言。这是覆盖所有后端业务行为的最高确定性缝，且正是前端消费的合约。
- **只测外部行为**：通过 HTTP 请求断言状态码、响应体、随后 GET 读回的一致性、WS 订阅收到的广播事件；不构造内部结构、不 mock service/数据库、不触碰实现细节。
- **必测场景**：无密钥/错密钥 401；每个实体 CRUD 全链路；级联删除链（删 workspace 后项目/任务/评论/活动全部消失）；position 排序语义（跨列移动、同列重排、整列 reindex 后顺序正确）；评论产生 activity 的副作用；WS 事件负载与项目隔离（A 项目事件不发给 B 项目订阅者）。
- **Prior art**：仓库当前零测试，本套件为第一个；参考仓库 kaneo 的后端测试位于其 apps/api（superstest 风格的 HTTP 级断言），本 spec 将其等价映射为 Go 的 httptest 模式。
- **前端不建测试基建**（用户已确认单缝）：前端经 `tsc --noEmit` 门槛 + 手工浏览器验证（真实拖拽、刷新保持、双窗口实时）。前端不承载业务逻辑，拖拽排序核心在服务端 position 语义，已被 API 缝覆盖。

## Out of Scope

- ADR-0003 全部后置候选：通知、搜索（FTS5）、自动化（Workflow Rule）、工时（time-entry）、MCP/AI 集成、公开分享
- 明确不做项：计费订阅、第三方集成（GitHub/Slack）、附件/文件存储
- 多用户 / 成员 / 角色 / 权限分级（Full-access Mode 的题中之义）
- 任务优先级、截止日期、循环/重复任务、子任务（kaneo 有但超出 Slim Scope）
- 前端单元测试与 E2E（Playwright）基建；i18n 多语言；深色主题
- 服务端渲染、鉴权以外的公开端点、多实例部署与 Redis

## Further Notes

- 本 spec 仅定义 M1 目标与测试缝，不随附实现。落地时可拆为两个内部分支：M1a 后端 API + API 缝测试、M1b 前端页面（对接 M1a 合约）。
- 主仓库当前零提交；建议以"spec 落盘"为首次提交点，后续每个里程碑独立提交。
- 实时性依赖单实例内存广播（ADR-0005）；未来若有多实例需求需另行 ADR 引入 Redis 或改用轮询。
- 拖拽的乐观更新与 WS invalidate 可能短暂不一致（乐观值 vs 服务端 reindex 值），以服务端广播为准收敛，前端不做冲突解决。
